## 1. Purpose & Ground-Truth Independence Mandate

This Annotation Guide governs both **automated scenario labeling** (for controlled failure injection across the target `1,500–1,800` traces, minimum `1,200`) and **human annotation** (for the mandatory `15–20%` manually reviewed subset and the `100–150` double-annotated inter-annotator agreement subset defined in Proposal `Section O.3`).

> **Hard Non-Leakage Invariant:** Ground-truth labels (`primary_label`, `secondary_findings`, `ground_truth_root_cause`) **must never be derived from, pre-populated by, or adjudicated using the predictions of the evaluator, LLM-as-a-judge, rule classifier, Logistic Regression, or XGBoost model under test.**

---

## 2. Ground-Truth Hierarchy & Provenance Sources

Every labeled trace record in `datasets/labels/` must carry a `label_provenance` object distinguishing three independent sources of truth:

1. **Tier 1 — Controlled Scenario Injection Provenance (`INJECTION_RECIPE_AND_DETERMINISTIC_VERIFICATION`):**
   - For seeded traces generated by Nour's scenario runner (`scenarios/`), the scenario manifest records `injected_failure_class`, `injected_root_cause`, `injection_recipe_id`, `expected_relevant_doc_ids`, and `expected_critical_policy_result`.
   - **Observed-Mechanism Verification Rule (Seeded vs. Observed Failure):** An injected perturbation does *not* automatically become the final ground-truth label if the application did not actually exhibit the failure mechanism. Specifically:
     - If a scenario seeds a degraded prompt intended to induce `WORKFLOW_VIOLATION`, **and** the trace records a `tool_proposal` in `PRE_APPROVAL` (`approval_received == false`), the observed mechanism confirms `primary_label = "WORKFLOW_VIOLATION"`.
     - If a scenario seeds a high-temperature or distractor prompt intended to induce `HALLUCINATION`, **but** the LLM still produces a 100% grounded, accurately cited answer (or properly abstains), the trace must **not** be labeled `HALLUCINATION` merely because the injection recipe ran. Ambiguous semantic injections must either pass a deterministic symptom sanity check (e.g., missing citation / contradicted numeric span) or be routed to **Tier 2 Human Review**.
2. **Tier 2 — Blind Human Adjudication (`HUMAN_SINGLE_REVIEW` & `HUMAN_DOUBLE_ANNOTATED_ADJUDICATED`):**
   - Human annotators inspect `15–20%` of the final dataset (`~225–360` traces), prioritizing `HALLUCINATION`, `RETRIEVAL_FAILURE`, `PROMPT_INJECTION`, and multi-failure agent trajectories.
   - Annotators view the **raw trace envelope** (`request`, `versions`, `events[]`, and corpus reference documents) in a blind annotation view where **all post-run evaluator scores, LLM-judge rationales, classifier predictions, and RCA outputs are hidden**.
3. **Tier 3 — Independent Domain Truth Tables (`POLICY_AND_SCHEMA_ORACLE`):**
   - For procurement policies (`PROC-APPROVAL-01`, `PROC-TOOL-STAGE-01`, `PROC-SUPPLIER-01`) and tool schemas, ground truth is defined by the formal mathematical specification of the business rules applied to `request.structured_input` and the mock supplier/approval database state.

## 3. Class Precedence Hierarchy for Multi-Failure Trajectories

When a single trace exhibits multiple failure mechanisms simultaneously, annotators and label validators must apply the following strict **5-Tier Causal & Adversary Precedence Order** to select the single `primary_label` and place all remaining observed failures into `secondary_findings`:

```text
Tier 1 (Highest): PROMPT_INJECTION          (Adversarial root trigger overrides induced downstream symptoms)
       ↓
Tier 2:           RETRIEVAL_FAILURE         (Upstream missing context overrides downstream ungrounded generation)
       ↓
Tier 3:           TOOL_SELECTION_ERROR      (1st in Tier 3: Selecting the wrong tool overrides stage/argument checks on that tool)
                  WORKFLOW_VIOLATION        (2nd in Tier 3: Skipping stages / premature tool proposal in PRE_APPROVAL overrides argument errors on the same call and resulting policy breach)
                  INVALID_TOOL_ARGUMENTS    (3rd in Tier 3: Corrupted arguments on a stage-valid tool call)
       ↓
Tier 4:           POLICY_VIOLATION          (Substantive business policy breach when workflow sequence was otherwise valid)
       ↓
Tier 5 (Lowest):  UNSUPPORTED_COMPLETION    (1st in Tier 5: False action-success claim when no upstream Tier 1–4 violation occurred first)
                  HALLUCINATION             (2nd in Tier 5: Ungrounded knowledge/policy answer when retrieval succeeded and no upstream violation occurred)
```

### 3.1 Deterministic Same-Tier Tie-Breaking Rule (`TB-SAME-TIER-V1`)

When a single trace exhibits two or more failure classes belonging to the **same precedence tier** (specifically within **Tier 3**: `TOOL_SELECTION_ERROR`, `WORKFLOW_VIOLATION`, `INVALID_TOOL_ARGUMENTS`; or within **Tier 5**: `UNSUPPORTED_COMPLETION`, `HALLUCINATION`), annotators and automated rule/ML validators MUST resolve the tie using the following 4-step deterministic sequence (matching `governance_rules.same_tier_tie_breaker` in [`../../packages/reliability-engine/src/trustops_reliability/taxonomy/failure_taxonomy.yaml`](../../packages/reliability-engine/src/trustops_reliability/taxonomy/failure_taxonomy.yaml)):

1. **Step 1 — Earliest Causal Event (`sequence_number` / `timestamp`):** If the co-occurring same-tier failures originate on distinct trace events, assign `primary_label` to the class whose earliest supporting causal event has the lower `sequence_number` (occurred first in time), and place the later class in `secondary_findings`.
   - *Example (Different Events in Tier 3):* If the agent calls `get_supplier` at `e2` with malformed arguments (`INVALID_TOOL_ARGUMENTS`) and later proposes `create_purchase_order` at `e6` while still in `PRE_APPROVAL` (`WORKFLOW_VIOLATION`), `INVALID_TOOL_ARGUMENTS` (`e2`) is the `primary_label` and `WORKFLOW_VIOLATION` (`e6`) is placed in `secondary_findings`.
2. **Step 2 — Structural & State-Machine Precondition Priority (Same Triggering Event):** If two same-tier failure classes occur on the **exact same triggering event** (identical `event_id` / `sequence_number`), select the structural or state-machine precondition failure over the parameter-level or span-fabrication defect:
   - **Tier 3 Same-Event Resolution (`TOOL_SELECTION_ERROR` $\succ$ `WORKFLOW_VIOLATION` $\succ$ `INVALID_TOOL_ARGUMENTS`):**
     - If the wrong tool is selected for the user's intent (`TOOL_SELECTION_ERROR`), it supersedes stage and parameter checks on that invocation.
     - **Co-occurring `WORKFLOW_VIOLATION` + `INVALID_TOOL_ARGUMENTS` on the same tool proposal/call:** Always assign **`primary_label = "WORKFLOW_VIOLATION"`** and record **`"INVALID_TOOL_ARGUMENTS"` in `secondary_findings`** (alongside `"POLICY_VIOLATION"` if blocked by pre-tool policy check). *Engineering Rationale:* State-machine stage validity is a structural precondition for tool invocation—if `create_purchase_order` is forbidden in `PRE_APPROVAL` because manager approval has not been obtained, the agent had no authority to invoke that tool in that state regardless of whether `quantity` or `estimated_cost` was well-formed (see Worked Example **`EX-11`** in Section 7).
   - **Tier 5 Same-Event Resolution (`UNSUPPORTED_COMPLETION` $\succ$ `HALLUCINATION` on `final_response`):** If `final_response` simultaneously falsely claims a business action/PO was created (`UNSUPPORTED_COMPLETION`) and states an ungrounded policy fact (`HALLUCINATION`) with no upstream Tier 1–4 failure, assign **`primary_label = "UNSUPPORTED_COMPLETION"`** and record **`"HALLUCINATION"` in `secondary_findings`**.
3. **Step 3 — Prediction-Only Severity Tie-Breaker:** During prediction processing only, if candidates remain tied, select the class whose evaluator finding has higher severity (critical > high > medium > low). Ground-truth annotators and label-generation tools MUST skip this step and proceed directly to Step 4 (Canonical Intra-Tier Order). Evaluator outputs MUST NOT influence ground-truth labels.
4. **Step 4 — Canonical Intra-Tier Order:** As a final deterministic fallback, select the class listed first in `precedence_hierarchy.classes` in `failure_taxonomy.yaml`.

* **Verification against Proposal v1.1 Canonical Examples:**
  - In `tr_proc_102` (`Proposal §J.2` & `Figure 3`): Observed failures are `WORKFLOW_VIOLATION` (Tier 3), `POLICY_VIOLATION` (Tier 4), and `UNSUPPORTED_COMPLETION` (Tier 5). Applying the precedence rule yields **`primary_label = "WORKFLOW_VIOLATION"`** and **`secondary_findings = ["POLICY_VIOLATION", "UNSUPPORTED_COMPLETION"]`**, matching Proposal `J.2` (`"failure_prediction": {"label": "WORKFLOW_VIOLATION"}`) and `Figure 3` (`POLICY / WORKFLOW VIOLATION` + `UNSUPPORTED_COMPLETION`).
  - In `tr_rag_210` (`Proposal §J.3`): Observed failures are `RETRIEVAL_FAILURE` (Tier 2) and `HALLUCINATION` (Tier 5). Applying the precedence rule yields **`primary_label = "RETRIEVAL_FAILURE"`** and **`secondary_findings = ["HALLUCINATION"]`**, matching Proposal `J.3` (`"failure_prediction": {"label": "RETRIEVAL_FAILURE"}`).

## 4. Handling Ambiguous or Insufficient Trace Evidence

1. **Missing Required Trace Events (`QUARANTINED_INSUFFICIENT_EVIDENCE`):**
   - If a trace is truncated or missing required events (e.g., an agent trace with no `final_response` and no `tool_result`, or a RAG trace with no `retrieval` event), annotators must mark `annotation_status = "QUARANTINED_INSUFFICIENT_EVIDENCE"` with a mandatory `quarantine_reason_code` (`MISSING_RETRIEVAL_EVENT`, `MISSING_FINAL_RESPONSE`, `TRUNCATED_EVENT_CHAIN`, `MISSING_VERSION_PROVENANCE`).
   - Alaa's dataset pipeline (`S3-05`) excludes quarantined records from training/validation/test splits and logs them in the quarantine report rather than guessing a failure label.
2. **Borderline Semantic Cases (`AMBIGUOUS_ESCALATED`):**
   - When an annotator cannot determine whether a claim is a `HALLUCINATION` or an acceptable paraphrase of `content_snippet`, the trace is flagged `annotation_status = "AMBIGUOUS_ESCALATED"` and routed to a second independent annotator plus lead adjudication (Ahmed + Nour).

## 5. Double-Annotation, Disagreement Escalation & Reproducibility Protocol

1. **Double-Annotation Sampling (`100–150` Traces):**
   - Stratified across all 9 classes (`~12–18` traces per class), oversampling `HALLUCINATION`, `RETRIEVAL_FAILURE`, `PROMPT_INJECTION`, and compound `WORKFLOW_VIOLATION` + `UNSUPPORTED_COMPLETION` cases.
2. **Independent Blind Pass:**
   - Annotator A (Ahmed) and Annotator B (Nour or Alaa) independently assign `primary_label`, `secondary_findings`, `ground_truth_root_cause`, and `supporting_event_ids[]`.
3. **Agreement Metrics Computed Before Adjudication:**
   - Compute unweighted **Cohen's $\kappa$** on the 9-class `primary_label`:
     $$\kappa = \frac{p_o - p_e}{1 - p_e}$$
     where $p_o$ is observed exact agreement and $p_e = \sum_{c=1}^{9} p_{A,c} \cdot p_{B,c}$ is chance agreement.
   - Compute binary **Cohen's $\kappa$** on `HALLUCINATION` groundedness and `PROMPT_INJECTION` attack verdicts, plus **Jaccard overlap** on `secondary_findings`.
   - Per Proposal `Section O.3`, report the actual measured $\kappa$ without assuming a target value in advance.
4. **Disagreement Escalation & Adjudication Log:**
   - Every disagreement between Annotator A and Annotator B is resolved in a joint adjudication session referencing the specific `event_id`s and the Precedence Hierarchy in Section 3. Both pre-adjudication labels (`annotator_a_label`, `annotator_b_label`) and the final `adjudicated_label` + `adjudication_rationale` are preserved immutably in `datasets/labels/` so agreement statistics can always be regenerated.

## 6. Dataset Leakage Prevention Rules for Annotation & Splitting

To satisfy Proposal `Section L.3` and `Section O.4`:
1. **Group-Key Construction (`split_group_key`):** Every trace is assigned a composite grouping key:
   $$\texttt{split\_group\_key} = \texttt{scenario\_family} \mathbin{\Vert} \texttt{question\_template\_id}$$
   *(Note: Per Proposal Section L.3, splitting is performed by scenario family, question template, and failure-injection recipe rather than random rows so that all paraphrases from one base scenario remain inside the same split (`train`, `val`, or `test`), while stratified group splitting preserves failure-injection recipe and class balance across the 70% / 15% / 15% splits.)*
2. **Strict Feature Projection Stripping:** Before any trace enters `packages/reliability-engine/src/trustops_reliability/feature_engineering/`, Mohab's and Alaa's export adapter strips `scenario_metadata`, `source_metadata.is_poisoned_test_doc`, and all `datasets/labels/` fields.
