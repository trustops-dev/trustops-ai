## Claim-boundary requirements

1. Build the proposal and policy check from the active request revision and trusted supplier/approval evidence. Capture the approval record identity/version if required, supplier record identity/version, and check/argument binding in trusted runtime context. These are review requirements, **not new model-visible tool arguments or established canonical field names**.
2. On the same root-scoped, single-use claim path, resolve current authoritative record versions and verify they equal the versions bound to the accepted check. The ordering of each authority's own records follows its source record sequence. Do not compare unrelated approval and supplier sequence numbers as though they shared a clock or transaction log.
3. Consume the allowance and dispatch only after the bound ALLOW and currentness verification can be made indivisible or otherwise fenced against concurrent changes under the agreed platform contract. If the platform cannot establish that guarantee, return an explicit non-dispatch outcome and retain the last confirmed application state. Mohab and Mohamed must specify the transaction/lease/fencing evidence and the separate immutable consumption record required by OD-12-CLAIM.
4. An authorization check or version check that fails before dispatch produces no PO invocation and no claimed effect. An uncertainty **after** dispatch remains UNKNOWN until authoritative read-only reconciliation; it must not be reclassified as no effect because approval later changed.
