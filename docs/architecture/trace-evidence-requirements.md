### 1.1 Trajectory Sequence Invariants & Lifecycle Contracts

To eliminate ambiguity across tool lifecycle events, the Reliability Engine establishes four strict canonical trajectory contracts based on pre-tool governance and operational outcomes:

```
[Trajectory A: Allowed Tool Execution]
tool_proposal ──> argument_validation ──> policy_check (ALLOW) ──> tool_call ──> tool_result ──> final_response

[Trajectory B: SC-03A Early Business Stop (NORMAL)]
request ──> tool_call (get_supplier: NOT_APPROVED) ──> agent_state (POLICY_CHECKED / STOPPED_BUSINESS_BLOCK) ──> final_response

[Trajectory C: Pre-Execution Blocked Proposal]
tool_proposal ──> argument_validation ──> policy_check (BLOCK) ──> tool_suppression ──> final_response

[Trajectory D: Timeout with Recovery Reconciliation]
tool_proposal ──> argument_validation ──> policy_check (ALLOW) ──> tool_call ──> tool_result (TIMEOUT)
      │
      └──> recovery_check (RESOLVED_COMMITTED | STILL_UNRESOLVED) ──> final_response
```

1. **Trajectory A — Allowed & Dispatched Tool Call (`action_verdict == "ALLOW"`, e.g., `tr_proc_101`, `tr_proc_112`):**
   - **Canonical Sequence:** `tool_proposal` $\rightarrow$ `argument_validation` $\rightarrow$ `policy_check` (`action_verdict = "ALLOW"`) $\rightarrow$ **`tool_call` (`call_id` populated)** $\rightarrow$ **`tool_result` (`call_id` populated, `execution_status` $\in$ `{"COMPLETED", "TIMEOUT", "RUNTIME_EXCEPTION"}`, `side_effect_state`)** $\rightarrow$ `final_response`.
   - **Strict Invariant:** Both `tool_call` and `tool_result` are mandatory, sharing an identical non-null `call_id`. Application success requires `tool_result.result_payload.status in ["CREATED", "ALREADY_EXISTS"]` and `side_effect_state in ["COMMITTED", "ALREADY_EXISTING"]`.
   - **ABSENT:** `tool_suppression` is forbidden.
2. **Trajectory B — SC-03A Early Business Stop (Truthful Business Rejection — `NORMAL`, e.g., `tr_proc_119a`):**
   - **Canonical Sequence:** `request` $\rightarrow$ `tool_call` (`get_supplier` $\rightarrow$ `result_payload.status: "FOUND"`, `supplier.status: "NOT_APPROVED"`) $\rightarrow$ `agent_state` (`POLICY_CHECKED` / `STOPPED_BUSINESS_BLOCK`) $\rightarrow$ `final_response`.
   - **Strict Invariant:** The agent truthfully checks supplier eligibility and halts progression cleanly without generating a `create_purchase_order` proposal.
   - **ABSENT:** No `create_purchase_order` proposal, PO `policy_check`, `tool_suppression`, or PO dispatch occurs. This legitimate business rejection is a valid execution trajectory and is classified as **`NORMAL`** (baseline valid trajectory, not a failure).
3. **Trajectory C — Pre-Execution Blocked Proposal (`action_verdict == "BLOCK"`, e.g., `tr_proc_102`, `tr_proc_130`, `tr_proc_119b`):**
   - **Canonical Sequence:** `tool_proposal` $\rightarrow$ `argument_validation` $\rightarrow$ `policy_check` (`action_verdict = "BLOCK"`) $\rightarrow$ `tool_suppression` (`suppression_source = "PRE_TOOL_POLICY_GATE"`, `blocking_check_id = "chk_102"`, `blocking_policy_ids = ["PROC-APPROVAL-01", "PROC-TOOL-STAGE-01"]`, `execution_started: false, tool_dispatched: false, side_effect_state = "NONE"`) $\rightarrow$ `final_response`.
   - **Strict Invariant:** **No `tool_call` or synthetic `tool_result` event is emitted.** It is an explicit architectural rule that `tool_call` is **NEVER emitted or required on pre-execution blocked proposals**. Evaluators (`det_tool_arguments_v1`, `agent_workflow_and_completion_v1`, `pol_conformance_adapter_v1`) inspect `tool_proposal.proposed_arguments`, `policy_check`, and `tool_suppression` without expecting execution events.
4. **Trajectory D — Timeout with Recovery Reconciliation (e.g., `tr_proc_125`):**
   - **Canonical Sequence:** `tool_call` $\rightarrow$ `tool_result` (`execution_status = "TIMEOUT"`, `result_payload.status = "UNKNOWN_OUTCOME"`, `side_effect_state = "UNKNOWN"`) $\rightarrow$ `recovery_check` $\rightarrow$ `final_response`.
   - **Strict Invariant:** Action execution is proven recovered **only if** `recovery_check.reconciliation_status == "RESOLVED_COMMITTED"` and `recovery_check.resolved_side_effect_state == "COMMITTED"`. If `recovery_check` yields `reconciliation_status == "STILL_UNRESOLVED"`, the outcome remains unverified; claiming execution in `final_response` constitutes `UNSUPPORTED_COMPLETION`.
